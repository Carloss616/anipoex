# Extension runtime: match Mihon's host

Extensions run against whatever the host puts on the classpath, so the host follows Mihon.

- **Libraries and versions come from Mihon's [`gradle/libs.versions.toml`](https://github.com/mihonapp/mihon/blob/main/gradle/libs.versions.toml)** (coroutines, OkHttp, jsoup, QuickJS, imagedecoder), capped only where a version needs a Kotlin compiler past the app's. A `NoSuchMethodError` or `NoClassDefFoundError` from an extension means the host is behind (`runBlockingK` came from coroutines 1.11).
- **Network classes are ports of Mihon's** (`@see` at the top of each); diff against the upstream file before changing behaviour. The client keeps cookies (`AndroidCookieJar`), and Android solves Cloudflare in a WebView. The JVM's `CloudflareInterceptor.jvm.kt` asks the app through `Host` (desktop: `desktop/host/challenge.js`; iOS: `ChallengeHost.swift`): the browser solves as itself, and that host's requests then go out from the solved page, since some sites tie the clearance to the browser's TLS fingerprint and refuse it from the JVM or curl. Never rewrite the challenge browser's user agent: Electron's with the `Electron/` token stripped reads as spoofed (no matching client hints) and Turnstile then refuses even a person's click; the stock one clears a challenge on its own in ~4 s.
- **A challenge belongs to the host that sent it, not the one requested**: a source's old domain can 301 to a new one that challenges, and the clearance lands there. `CloudflareInterceptor.jvm.kt` solves `response.request.url` and sends the old host's later requests to the new one, since the solved page can't fetch across origins; Android's `CloudflareInterceptor.kt` solves and checks the clearance there too, and OkHttp's redirect carries it (upstream Mihon reads the original URL, and fails the bypass). A redirect counts as a move only when the path stays the same: otherwise one link to a partner site would send the whole source there. Cloudflare can also let the browser through with no clearance at all, so a page whose main frame loaded without an HTTP error ends the wait (`desktop/host/challenge.js`, iOS `ChallengeHost.swift`'s `StatusWatcher`; not the page title, which Cloudflare translates), and with `Host.fetch` a missing `cf_clearance` isn't a failure: only that page reaches the site.
- **What the JVM can't run, the app lends through `Host`**: `QuickJs` evaluates in the app's own engine (`desktop/host/javascript.js`: an isolated world per engine in a hidden page with no network; iOS `ScriptHost.swift`: a `JSContext`), since QuickJS's JNI library can't load there and pure-Java engines (Rhino) don't parse the `class` syntax sites' scripts use. Android's crypto names the JVM lacks get a provider (`Pkcs7Padding.kt`: the extensions' AES helper asks for `AES/CBC/PKCS7PADDING` and swallows the failure). `android.graphics` keeps no pixels: a `Bitmap` is its encoded image plus the draws recorded on it, and `compress()` hands them to the app in one `renderImage` call (`ImageEngine.kt`; `desktop/host/graphics.js`, a hidden page's canvas; iOS `GraphicsHost.swift`, Core Graphics), since the iOS JDK is java.base only. Text is laid out in the JVM with Helvetica's widths (`Paint.measureText`, `Layout.wrap`) and each host draws those lines in Helvetica, so a page sized from `Layout.getHeight` fits its text; a host never re-wraps. Its line breaks are its own: the iOS JDK ships `java.text` without its rule data (`BreakIterator` fails with `Can't load sun/text/resources/LineBreakIteratorData`), so try anything from `java.text` on the simulator, not only the desktop JVM. `getPixels`/`setPixels` have the engine draw the bitmap once as PNG and keep its pixels until something is drawn on it (`Png.kt`). `BitmapFactory` only reads a size from the header (`ImageEngine.size`): a format it can't read returns null, and sources then fall back to Mihon's native decoders, which the JVM lacks ("No decoder could read the image"): teach `size` the format, and the hosts decode it. `android.webkit.WebView` drives a page the app owns through the `wv*` calls (`WebView.kt`; the page's side comes back as long-polled `wvEvents`), and `Dispatchers.Main` is the main `Looper`'s thread (`MainDispatcher.kt`), so the extensions' WebView helper runs as on Android and its Chromium probes fail into its fallbacks. Bot checks (Turnstile) inside those pages pass only if the browser looks like what it claims: desktop intercepts through the DevTools `Fetch` domain, never `protocol.handle` (its forwarded requests lose their `Sec-Fetch-*` headers), and gives an extension's user agent matching client hints (`desktop/host/webview/protocol.js` `uaOverride`); iOS keeps Safari's user agent when an extension asks for Chrome's (WebKit can't pass for Chromium) and answers the load with it, and the runtime then sends that site's requests as Safari too (`Host.browserUserAgents`), since its session is Safari's; WebKit can't hold http(s) requests, so the page's fetch and XHR wait in an injected wrapper for the interceptor's answer (with the headers WebKit would add: sources replay them) and navigations are only reported. Cookies a page gains after it finished (a site's session) reach the CookieManager through `cookies` events: on iOS one goes ahead of every event, since WebKit's cookie observer never fires for that store. iOS writes the runtime's stderr to `extensions/server.log`, like desktop.
- **dex2jar's output needs repairs before the JVM loads it** (`DexTranslator.kt`, one test per case): R8's inlined constructors, `java/util/Object` in frames, and static or private calls to an interface's method written as a class's (those classes go to version 52; measured on current APKs: one class in 142, none broken).
- **Reader pages go through the source**, as Mihon's `getImage`: the runtime's `image` call downloads with the source's client and `imageRequest` into `PageCache.kt`, and the reader shows that file (desktop: main's `anipoex-page://` scheme serves it). Never show a page's `imageUrl` directly: descramblers (keyed on a URL fragment such as `#scramble`, or in a client interceptor) only run there.
- **Covers go out with the source's `HttpSource.headers`**, as Mihon's `MangaCoverFetcher` does: some image hosts refuse a request without the site's Referer. `installed()` hands them per source; desktop adds them in main (`desktop/assets/covers.js`), since headers on a web `<img>` make it a CORS fetch. On Android, Glide's `GlideUrl` loader is the runtime's client (DNS over HTTPS, cookies).
- **Known gaps, left on purpose** (a catalog scan reports them; don't reinvestigate): `android.icu.text` (one extension; `NoClassDefFoundError: android/icu/text/SearchIterator` before it lists, since it names `StringSearch`, `Collator`, `RuleBasedCollator`, `Normalizer2` and `BreakIterator`, and `StringSearch` has no `java.text` counterpart to bridge to); `Canvas` shapes (`drawLine`, `drawCircle`, `drawPath`, `drawRoundRect`) throw, since the catalog draws them only in `Drawable`s, which nothing here renders; a font a source loads itself (`Typeface.createFromFile`, translation overlays) draws in Helvetica, and `clipRect` is missing.
- **Measure parity on the catalog, not one source**: scan the index's jars for classes and members the runtime lacks (a class only named in a field or signature still counts: the verifier loads it, and one extension's failure there blocks every method of the class that names it), and run install + popular + search across a language (`jvm/tools/smoke-install.ts` covers install).
